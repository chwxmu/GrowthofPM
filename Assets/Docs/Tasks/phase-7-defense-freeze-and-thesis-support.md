# Phase 7：答辩封版与论文支撑收口

## 前置条件

- `P0` ~ `P6` 已完成到当前候选基线，项目已经具备从 `MenuScene` 进入并完整跑通 `P1 -> P2 -> P3 -> GameSummaryPanel` 的主闭环。
- 当前基线已完成一轮 `Phase 6` 低风险收口，详见：
  - `Assets/Docs/TaskReports/20260330/20260330_Phase6有限抛光与答辩演示收口.md`
- 当前自动化基线为：`83 passed / 0 failed / 0 skipped`
- 用户已完成一轮人工彩排，并反馈“没有什么问题”。

## 阶段定位

`Phase 7` 不再是继续扩玩法功能，而是把项目从“答辩演示候选版”推进到“可冻结、可提交、可支撑论文展示”的最终收口阶段。

这一阶段的核心目标有两条：

1. **封版候选版冻结**：把当前工程基线稳定下来，避免在答辩前继续引入主流程回归。
2. **论文与答辩支撑材料收口**：围绕 AI 建议查看率、采纳率、决策耗时、P3 质量标签拆分等研究点，补齐可截图、可说明、可复现的展示材料。

## 本阶段优先级

1. 最终回归与封版候选版冻结
2. 研究数据口径确认与展示材料整理
3. 演示资产与交付物整理
4. 仅在发现明确阻塞时，做最小必要修复

## 非目标（本阶段不要做）

- 不新增剧情、小游戏或新的玩法系统。
- 不做大规模 UI 改版、场景重做、音频资源全面接入。
- 不重写 `GameManager`、`StoryManager`、`UIManager` 等主架构。
- 不因为“还能更好看”而继续扩大 polish 范围。
- 不在没有明确答辩/论文价值的前提下新增复杂数据导出系统。

## 第一包：封版候选版冻结

### 目标

把当前版本从“看起来稳定”推进到“可明确冻结”的状态。

### 重点任务

1. 重新确认：
   - Unity MCP 编译通过
   - Unity 控制台无新的项目级 `error`
   - EditMode 全量测试继续通过
2. 复查核心链路：
   - `主菜单 -> 新游戏`
   - `主菜单 -> 继续游戏`
   - `P2 -> P3 -> GameSummaryPanel`
   - `GameSummaryPanel -> 重新开始 / 返回主菜单`
3. 只接受两类改动：
   - `P0` 阻塞级 bug 修复
   - 直接影响答辩或论文展示的低风险修正
4. 若本轮无阻塞问题，尽快冻结为“答辩候选版”，不要继续做开放式优化。

### 通过标准

- 自动化、编译、控制台、主链路均通过
- 没有新的高优先级缺陷
- 可以明确给出“当前版本是否建议冻结”的结论

## 第二包：研究数据口径与论文支撑材料

### 目标

让项目中的研究数据从“已埋点、已展示”进一步升级为“论文中可引用、答辩中可解释”。

### 重点任务

1. 冻结并核对以下统计口径：
   - 全局 AI 采纳率
   - 按项目采纳率（P1 / P2 / P3）
   - AI 建议查看率
   - 决策总数 / 查看次数 / 采纳次数
   - P3 `good / neutral / bad` 建议采纳率
   - 决策耗时记录口径（记录方式、展示方式、是否取均值/区间）
2. 若当前运行时展示已足够支撑论文，不强制新增系统；优先：
   - 整理统计口径说明文档
   - 准备代表性截图或数据示例
3. 若当前口径对论文说明仍不够清晰，只允许做**最小读侧增强**，例如：
   - 补一个只读辅助方法
   - 补一个编辑器侧/调试侧数据查看入口
   - 补一个轻量文本导出工具
4. 不为了“导出漂亮图表”引入额外重型依赖。

### 通过标准

- 能清楚回答“系统记录了什么、怎么算、在哪里展示”
- 关键研究指标可通过界面、日志、导出文本或截图材料稳定说明
- 不因为研究材料整理而破坏游戏主流程

## 第三包：答辩展示资产整理

### 目标

把工程成果整理成便于展示和讲解的材料，而不是把所有说服力都压在现场临时点击上。

### 建议整理项

1. 关键截图：
   - 主菜单
   - 对话面板
   - 决策面板 + AI 建议
   - `CPMGamePanel`
   - `RiskDashboardPanel`
   - `TransitionPanel` / `EndingPanel`
   - `GameSummaryPanel`
2. 关键流程说明：
   - 周循环流程图
   - `P2` 隐藏风险与因果链说明
   - `P3` 建议质量标签与采纳分析说明
3. 演示运行准备：
   - 如有需要，准备一个稳定可演示的存档起点
   - 明确答辩现场演示路线（建议主链路与备用路线）
4. 如时间允许，再准备一个 Windows 演示包或封存构建记录。

### 通过标准

- 不依赖临场解释也能看出系统核心亮点
- 关键玩法、研究点、总结页都有可直接展示的材料

## 第四包：最终验证与归档

### 目标

在真正封版前，给出一份可以回看、可以归档、可以支撑提交的最终记录。

### 重点任务

1. 再执行一轮最终验证：
   - EditMode 全量测试
   - Unity MCP 编译 / 控制台检查
   - 主链路手工复测
2. 归档本阶段结果：
   - 修改文件列表
   - 测试结果
   - 截图 / 数据材料路径
   - 当前版本冻结建议
   - 剩余风险
3. 若进入提交阶段，再准备：
   - 提交说明
   - 版本说明
   - 答辩演示注意事项

### 通过标准

- 有完整归档记录
- 有清晰的“可冻结 / 需继续修”的结论
- 即使换一个执行者，也能快速理解当前项目状态

## 推荐执行顺序

1. 先做最终验证，判断当前版本能否冻结
2. 在不破坏稳定性的前提下整理论文统计口径与展示材料
3. 再整理截图、演示路线、构建结果与归档文档
4. 若中途发现明确阻塞，再回到最小修复；否则停止继续加需求
