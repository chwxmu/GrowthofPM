# 任务报告：修复自动化测试 8 条失败用例

## 任务背景
在 `Phase2Flow7To12Tests` 复测中出现 8 条失败用例，失败点集中在 `GameManager.Instance` / `StoryManager.Instance` 的正向调用链路（结算、周推进、结局评估、面板展示、答题加精力）。本次任务目标是定位共同根因并恢复流程 7-12 的自动化测试稳定性。

## 修改文件
- `Assets/Scripts/Core/Singleton.cs`
- `Assets/Tests/Editor/Phase2Flow7To12Tests.cs`
- `Assets/Docs/TaskReports/20260319/20260319_修复自动化测试8条失败用例.md`

## 核心逻辑
1. 根因定位
- 失败样例共性为依赖 `Singleton<T>.Instance`。
- `Singleton<T>` 中 `_isShuttingDown` 置位后会直接返回 `null`，在 EditMode 测试链路中可能残留静态状态，导致后续 `Instance` 访问全部短路。

2. 修复策略
- 在 `Instance` getter 中，当 `_isShuttingDown == true` 时，优先尝试重新绑定场景中已存在实例；若处于 Editor 非 Play 状态，则允许复位 `_isShuttingDown`。
- 在 `Awake()` 中显式复位 `_isShuttingDown = false`，确保新实例初始化后可正常参与单例分发。

3. 影响范围
- 不改业务规则，只修复单例可用性。
- 直接恢复 `QuizPanel` 加精力、`StoryManager` 周结算/推进、`GameManager` 结局评估与项目推进、`EndingPanel/TransitionPanel` 文本与按钮逻辑。

4. 回归测试补充
- 在 `Phase2Flow7To12Tests` 中新增 `Singleton_InstanceShouldRecoverAfterApplicationQuitFlagInEditMode`。
- 用反射将 `Singleton<GameManager>` 的 `_isShuttingDown` 置为 `true` 后，再断言 `GameManager.Instance` 可恢复为已有实例，覆盖本次缺陷的核心触发条件。
