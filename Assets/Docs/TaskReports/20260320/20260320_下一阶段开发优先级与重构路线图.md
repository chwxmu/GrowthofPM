## 现阶段开发总原则

### 一、先补论文关键功能，再做体验型打磨

当前项目最重要的不是先做音频或视觉润色，而是先把以下几个论文核心点做完整：

- AI 建议采纳记录与即时保存
- P2 因果链与小游戏
- P3 AI 质量标签统计
- 最终总结面板与分析展示

### 二、保护现有“数据驱动周流程骨架”

现有项目最成熟的部分是：

- `DataManager` 读取 JSON
- `StoryManager` 驱动周流程
- 各主面板按阶段展示

因此后续开发应以“在现有骨架上补功能”为主，而不是重写主循环。

### 三、采用“边补功能、边收敛架构”的方式

当前架构已经暴露出技术债，但不适合一开始就大重构。更合理的方式是：

- 先做能直接支撑 Phase 4 / 5 的最小收敛
- 再在 Phase 4 / 5 完成后做一次模块拆分和 UI 规范化

### 四、避免过早进入 Phase 6 大范围润色

在 P2 小游戏、P3 统计面板、AI 质量记录还没完成之前，不建议投入大量精力做：

- 音频系统
- 设置面板
- 大规模动画润色
- 非关键 UI 美化

这些功能有价值，但论文展示价值不如核心机制闭环高。

## 下一阶段开发优先级

### P0：基线收口包（先做）

这是进入 Phase 3/4/5 正式开发前必须先处理的一小轮基线修正，用来降低后续返工风险。

#### 目标

- 稳定数据契约
- 修正实验记录与精力闭环
- 修正动态字体/资源路径等会持续影响调试的问题

#### 建议任务

1. **即时保存实验日志**
   - 决策完成后立即保存 `aiTrustRecords`
   - 保证论文数据不会因为中途退出而丢失

2. **修正 Quiz 与 Schedule 精力闭环**
   - 明确答题奖励是否计入“本周可分配精力”
   - 避免当前“显示加了精力，但安排时仍按基础精力计算”的不一致

3. **冻结 P2/P3 需要的新数据契约**
   - 为 P2 建立正式 `eventFlags` 方案（或等价字段）
   - 为 P3 明确 `AITrustRecord` 需要额外记录的项目号与 AI 质量标签

4. **修正动态字体显式绑定路径**
   - 确保运行时创建的 TMP 文本真正绑定规定的中文字体资源

5. **建立最小回归验证清单**
   - 每次阶段开发后至少验证：进入菜单、开始新游戏、进入对白、完成一次决策、打开日程、保存继续

#### 产出标准

- 基础主循环无明显回归
- 数据模型为 Phase 4 和 Phase 5 做好准备
- 后续任务不再频繁受“基础逻辑不一致”干扰

### P1：Phase 3 收口验收（紧随 P0）

虽然用户标记只有 Phase 1-2 完成，但从代码现状看，P1 内容已经大部分接入，因此下一步应优先把它正式验收收口，而不是继续半状态推进。

#### 目标

- 把 Project 1 变成稳定的“完整第一章”
- 为进入 P2 提供可信基线

#### 建议任务

1. 逐周验证 P1 的 9 周流程
2. 确认 Week 3 双决策周流程完全正确
3. 确认 P1 三档结局判定符合 `endings.json`
4. 确认失败时不会错误进入 P2
5. 确认成功/合格时能稳定进入 P2 转场
6. 确认中途存档、继续游戏能恢复到准确周数和项目

#### 产出标准

- P1 可从头玩到尾
- P1 可作为 Phase 4 开发的稳定入口
- 完成对应任务报告，视为 Phase 3 正式完成

### P2：Phase 4 核心实现（最高业务优先级）

这是下一阶段最重要的主开发包，因为它直接决定项目是否进入“特色机制真正成型”的阶段。

#### 必做功能

1. **抽离 `AIAdvisor` 基础模块**
   - 不要求一开始就完全重构所有 AI 逻辑
   - 但至少要把“AI 名称、建议读取、推荐选项、采纳统计”从 `GameManager` 里抽出一个清晰入口

2. **落地事件旗标系统**
   - 为 `cpmCorrect` 等因果事件建立可存档的数据结构

3. **实现 CPM 小游戏**
   - Week 3 正式进入小游戏，而不是占位跳过
   - 小游戏结果写回事件旗标

4. **接入 Week 5 因果链**
   - 当 CPM 失败时，触发 `conditionalEvent`
   - 正确体现“小赵暂停测试、老周回滚环境”的惩罚分支

5. **实现 Risk Dashboard 小游戏**
   - Week 9 正式进入限时点击逻辑
   - 风险变化正确写回 `hiddenRisk`

6. **接入 Week 11 `riskBasedDialogue`**
   - 让隐藏风险真正反馈到剧情表现层

7. **完成 P2 结局与转项目完整验证**

#### 产出标准

- P2 的隐藏风险、小游戏、因果链、风险对白与结局形成完整闭环
- Phase 4 结束后，项目应首次具备“论文特色机制可演示”的强展示能力

### P3：Phase 5 核心实现（最高论文优先级）

在 Phase 4 完整后，下一步应立即进入 P3 与总结统计，因为这是论文展示价值最高的一段。

#### 必做功能

1. **扩展 `AIAdvisor` 到 Project 3**
   - 支持 AI 名称切换为“混沌”
   - 接入 `aiQuality` 的记录逻辑

2. **补全 `AITrustRecord` 的统计字段**
   - 至少保证后续可以按项目、按质量分类做统计

3. **完整验证 P3 `dailyIntroDialogues` / `postDecisionDialogues`**
   - 因为代码看起来已经部分支持，这里重点是查漏补缺和验证，而不是从零实现

4. **实现 `GameSummaryPanel`**
   - 终局结局文本
   - 四维属性汇总
   - 总周数、决策数、答题数
   - 全局 AI 采纳率
   - 按项目采纳率
   - P3 按 `good / neutral / bad` 的采纳率拆分

5. **完成三项目完整串联验证**

#### 产出标准

- 完成论文答辩最关键的数据展示页面
- 三项目流程从开始到总结页形成闭环
- Phase 5 可正式视为完成

### P4：结构收敛式重构（在 Phase 4/5 完成后进行）

这一步不是为了“重写架构”，而是为了把已经证明需要存在的模块拆出来，降低后续维护难度。

#### 重构重点

1. **给 `GameManager` 减负**
   - AI 相关统计迁出到 `AIAdvisor` 或专门分析模块
   - 事件旗标与项目流程状态考虑收敛到 `StoryManager` 或独立状态容器

2. **减少字符串驱动**
   - 属性键、阶段键、小游戏类型尽可能收敛到枚举或常量映射

3. **减少 `FindObjectOfType` 依赖**
   - 优先对高频主面板做缓存引用或由 `UIManager` 提供统一获取

4. **回收静态 UI 到场景 / Prefab**
   - 特别是 `DialoguePanel`、`DecisionPanel`、`SchedulePanel`、`QuizPanel`
   - `EnsureLayout()` 从“造界面”降级为“修界面”

5. **清理旧资源与旧场景**
   - 明确 `HomeScene` 是否废弃
   - 明确 `Assets/Prefabs` 中哪些仍用于正式流程

#### 产出标准

- 不破坏现有玩法功能
- 让后续 Phase 6 与论文展示调样式时更容易维护

### P5：Phase 6 抛光与体验收尾（最后做）

在 Phase 4 和 Phase 5 都完成之后，再进入体验层抛光。

#### 建议执行顺序

1. 数值平衡
2. 关键 QA 与三项目全流程回归
3. 对话速度设置
4. 键盘快捷键 / 暂停 / QoL
5. UI 过渡与动画统一化
6. 音频系统与设置面板

#### 原因

- 这些内容很重要，但对“项目是否完成核心论文功能”并不是当前第一优先级。
- 若提前投入，会分散本应优先完成的 P2/P3 机制开发精力。

## 最终结论

结合现状分析和阶段任务文档，当前项目最合理的下一阶段路径不是继续平均推进所有任务，而是采用下面的优先级策略：

- **先做基线收口**，修掉会影响后续所有开发的数据与流程问题
- **再把 Phase 3 作为验收收口完成**，稳定第一项目闭环
- **然后把主要开发资源集中到 Phase 4 和 Phase 5**，因为它们承载了项目最重要的特色机制与论文展示价值
- **最后再做结构收敛与体验抛光**，避免过早美化导致主功能未闭环

简化成一句话就是：

`先稳主干，再补特色机制；先完成论文核心闭环，再做系统性重构和体验润色。`
