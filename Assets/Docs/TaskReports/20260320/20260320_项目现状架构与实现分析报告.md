## 总体架构结论

当前项目已经形成一条可运行的核心主干，其实际架构可以概括为：

`菜单场景 -> GameManager 启动 -> GameScene 场景初始化 -> StoryManager 驱动周流程 -> UI 面板按阶段切换 -> GameManager 统一结算状态 -> DataManager 持久化存档与配置数据`

从设计思想上看，项目仍然遵循 `AGENTS.md` 中提出的“单例 Manager + 数据驱动剧情”的方向，但目前的落地形态比目标架构更集中：

- `GameManager` 承担了全局状态、属性变更、隐藏风险、AI 记录、项目推进、结局判定等多项职责。
- `StoryManager` 实际承担了周循环状态机与主要 UI 流程调度，是当前最核心的玩法控制器。
- `UIManager` 只负责面板注册与显隐淡入淡出，不负责复杂 UI 状态机。
- `DataManager` 负责 JSON 配置读取与本地存档读写。
- 计划中的 `AIAdvisor`、`StatManager`、小游戏模块等尚未形成独立代码实现。

整体上，当前工程不是空壳，而是一个“主流程已打通、特色模块待补完”的中期版本。

## 总体架构拆解

### 1. 单例与运行时入口

- `Singleton<T>` 采用懒加载方式工作：当场景中不存在对应实例时，会自动创建一个新的单例 GameObject，并在 `Awake` 中 `DontDestroyOnLoad`。
- 这意味着管理器对象并不依赖场景预摆，而是运行时自动补齐，优点是方便调试，缺点是依赖关系较隐式。

### 2. 运行时主链路

- `MenuSceneController` 负责菜单按钮点击，调用 `GameManager.StartNewGame()` 或 `GameManager.ContinueGame()`。
- `GameManager` 负责载入 `GameScene`，并在场景加载完成后做统一初始化。
- 初始化时会：
  - 确保 `PlayerData` 与当前项目故事已就绪
  - 调用 `UIManager.RebuildPanelRegistry()` 重建面板注册表
  - 调用 `UIManager.HideAllPanels()` 关闭所有主面板
  - 刷新顶部状态栏
  - 调用 `StoryManager.HandleGameSceneLoaded()` 开始周流程
- `StoryManager` 接管周流程，从剧情对白开始，逐步进入决策、日程、答题、结算、结局与项目切换。

### 3. 数据驱动方式

- 项目剧情、决策事件、日程任务、题库、结局阈值全部来源于 `Assets/Resources/Data/` 下的 JSON 文件。
- 运行时通过 `Resources.Load<TextAsset>("Data/...")` 读取文本，再用 `JsonUtility` 反序列化到数据模型。
- 这种方式已经实现了“剧情与数值不硬编码进 C#”的核心目标，便于后续继续扩写剧情与实验数据。

## 按模块分析现有实现

### 一、Core 层

#### 1. `Singleton<T>`

- 作用：为各类 Manager 提供统一的单例基类。
- 实现特点：
  - 支持自动查找已存在实例。
  - 未找到时会临时创建 GameObject 并挂载对应组件。
  - 在 `Awake` 中做重复实例销毁。
  - 在 `OnApplicationQuit` 与 `OnDestroy` 中做关闭状态处理。
- 评价：实现完整，能够满足多场景切换下的单例存活需求。

#### 2. `GameConstants`

- 当前只定义了基础精力、答题奖励、初始属性值、三个项目周数等常量。
- 数量不多，说明项目虽然已经引入了常量类，但常量化还不彻底，部分关键字符串仍散落在业务代码中。

#### 3. `GameEnums`

- 已定义：`GameState`、`ProjectPhase`、`StatType`、`AIQuality`。
- 现状问题：
  - 枚举已经定义，但运行时代码对它们的使用并不充分。
  - 如阶段、属性键、AI 质量等仍有较多字符串比较。
- 评价：基础方向正确，但“类型安全”目标尚未完全落实。

#### 4. `GameManager`

- 当前是全局最核心的控制器之一，实际职责包括：
  - 当前游戏状态管理（菜单 / 游玩 / 暂停）
  - 当前玩家数据管理
  - 当前项目剧情数据缓存
  - 新游戏 / 继续游戏 / 切场景
  - 属性、精力、隐藏风险变更
  - AI 采纳率与决策记录写入
  - 当前项目结局判定
  - 直接在 `GameScene` 运行时的自动启动支持
- 优点：
  - 主流程入口集中，便于调试。
  - 结局判定与周数推进逻辑已打通。
  - 已具备实验记录字段与统计能力。
- 问题：
  - 职责过重，实际上承担了原计划中 `StatManager` 与部分 `AIAdvisor` 的职责。
  - 顶部状态条的刷新同时用了事件与直接查找两套方式，存在耦合。
  - 属性访问仍通过字符串键分派，维护成本偏高。

### 二、Manager 层

#### 1. `DataManager`

- 负责：
  - 按项目编号加载剧情 JSON
  - 加载日常任务库与答题题库
  - 加载结局配置
  - 本地存档保存、读取、删除
- 实现方式：
  - 配置数据：`Resources.Load<TextAsset>` + `JsonUtility.FromJson`
  - 存档数据：`Application.persistentDataPath/save.json`
- 优点：
  - 职责清晰，结构简单。
  - 空资源与解析异常处理较完整。
- 问题：
  - 仍依赖 `JsonUtility`，如果后续数据结构进一步嵌套，扩展能力有限。
  - 暂无数据版本迁移与兼容层。

#### 2. `UIManager`

- 负责：
  - 使用 `UIPanelMarker` 自动注册面板
  - 按面板名显示 / 隐藏面板
  - 统一给面板补 `CanvasGroup`
  - 使用 DOTween 做淡入淡出
- 实现特点：
  - 非常轻量，只做注册和播放动画。
  - 不做复杂状态机，不维护显式“当前活动主面板”字段。
- 评价：
  - 作为 UI 基础设施够用。
  - “同一时间只允许一个核心面板激活”这项约束主要依赖 `StoryManager.HideAllPanels()` 的调用顺序，并不是由 `UIManager` 强约束。

#### 3. `StoryManager`

- 这是当前玩法控制最完整的模块，负责整个“周循环状态机”。
- 已实现的流程阶段：
  - `Prologue`
  - `DailyIntro`
  - `Decision`
  - `Conditional`
  - `PostDecision`
  - `Schedule`
  - `Quiz`
  - `Settlement`
  - `Ending`
  - `Transition`
- 现有能力包括：
  - 启动一周流程
  - 读取当前周事件
  - 支持一周一次或两次决策
  - 支持条件事件
  - 支持后置对白与后置属性变化
  - 支持从日程页跳转答题再返回日程
  - 支持项目结束与跨项目转场
- 优点：
  - 周流程已经具备完整可玩链路。
  - 数据结构适配度高，能承接 P1/P2/P3 的不同剧情形式。
  - 设计上已经考虑实验记录、风险值、小游戏占位等后续扩展点。
- 问题：
  - 内部依赖大量 `FindObjectOfType`，模块耦合仍偏高。
  - 小游戏逻辑当前只是占位，没有真正进入独立玩法层。
  - `riskBasedDialogue` 尚未接入运行时流程。

### 三、Data 层

#### 1. `PlayerData`

- 已覆盖：
  - 四维属性
  - 当前精力
  - 当前项目 / 当前周

  - AI 信任记录列表

  - 是否采纳 AI
  - 是否查看 AI 建议
  - 是否跟随建议
  - 决策耗时
- 评价：
  - 结构已经能支撑论文中的“行为记录”需求。
  - 但“是否查看 AI 建议”目前不是通过实际交互采集，而是通过“事件是否存在 AI 建议文本”来近似判断，准确性不足。

#### 2. `StoryData`

- 当前数据模型已经比较完整，支持：

  - 条件事件

## 场景与资源组织分析

### 1. `GameScene`

- 当前实际运行的核心场景。
- 场景根对象极简，主要只有：
  - `GameCanvas`
  - `EventSystem`
  - `Camera`
- `GameCanvas` 下分为：
  - `TopStatusBar`
  - `PanelsRoot`
- `PanelsRoot` 下已有 6 个核心面板对象，但大多数面板的具体子结构并不依赖场景预摆，而是由脚本在运行时补建。
- 这说明当前 UI 组织方式更偏“面板占位 + 运行时构建”。

### 2. `MenuScene`

- 当前主入口菜单场景。
- 结构简单，符合当前代码实现方式。
- 与 `MenuSceneController` 的对象命名约定一致。

### 3. `HomeScene`

- 目前未在 Build Settings 中启用。
- 场景中存在大量不同命名风格对象，如 `DecisionCanvas`、`TopBar_Container`、`FuncBtn_Group` 等。
- 结合现有脚本来看，这更像旧版原型或历史 UI 方案，并未接入当前正式流程。

### 4. Prefab 使用现状

- `Assets/Prefabs` 中存在决策按钮、状态槽等预制体。
- 但从当前脚本引用来看，正式运行流程并未显著依赖这些 Prefab 去实例化主界面。
- 当前主流程的 UI 主要是场景占位 + 脚本自建布局，而不是“Prefab 驱动 UI 组合”。

## 当前实现方式总结

### 1. 强数据驱动，弱模块拆分

- 剧情、任务、题库、结局高度数据驱动，这一点完成度较高。
- 但代码模块拆分尚未完全达到设计目标，多个职责仍集中在 `GameManager` 与 `StoryManager`。

### 2. UI 偏运行时构建

- 多个 UI 面板在 `EnsureLayout()` 中动态创建子节点、按钮、文本、布局和滚动区。
- 好处是场景依赖少、可自动修复丢失引用。
- 代价是：
  - 脚本变长
  - 场景与脚本容易漂移
  - 不符合“静态 UI 优先在 Hierarchy / Inspector 修改”的项目规范

### 3. 跨模块通信仍偏直接查找

- 当前虽有事件机制，但并不彻底。
- 例如状态条既订阅事件，又被 `GameManager` 主动查找并刷新。
- `StoryManager` 内部大量使用 `FindObjectOfType` 去获取面板或状态栏对象，导致依赖隐式化。

### 4. 流程状态机已经成形

- 尽管结构上还有耦合，但“按周推进 + 分阶段展示 + 结算 + 自动保存 + 项目切换”已经形成稳定主流程。
- 这部分是当前工程最成熟、最有价值的成果。

## 关键缺口与待完善点

### 1. 规划模块尚未独立落地

- `AIAdvisor` 未实现为独立 Manager。
- `StatManager` 未实现，属性变更集中在 `GameManager`。
- `MiniGames` 目录及具体小游戏逻辑未落地。

### 2. P2 小游戏仍为占位

- `project2/story.json` 中已配置：
  - `cpm` 小游戏
  - `risk_dashboard` 小游戏
- 但两者目前都只有数据事件，没有真正的交互玩法脚本。
- 由于小游戏事件没有选项，`StoryManager` 当前会直接跳过这类事件。

### 3. `riskBasedDialogue` 未接入

- 数据模型与 P2 数据中已经存在按风险分层对白。
- 当前运行逻辑没有使用这部分内容，导致隐藏风险对剧情反馈的表现力不足。

### 4. `aiQuality` 未接入表现层

- P3 数据已经为每周 AI 建议标注 `good / neutral / bad`。
- 但现有 UI 与逻辑没有根据该字段做标签、颜色、信任反馈或行为影响。

### 5. 实验记录持久化不够及时

- 决策记录已写入内存中的 `PlayerData.aiTrustRecords`。
- 但并非每次决策完成后立即保存到本地存档。
- 这与研究日志“实时写入”的目标仍有偏差。

### 6. Quiz 与 Schedule 的精力闭环不完整

- 答题正确会给当前玩家加精力。
- 但打开日程安排时，面板仍按基础周精力初始化，而不是严格读取当前实时精力值。
- 这一点会导致“答题奖励精力”与“实际可分配精力”逻辑存在不一致。

### 7. 代码中仍有较多字符串驱动

- 面板名、属性键、阶段、小游戏类型等仍大量使用字符串。
- 与“避免魔术字符串”的规范相比，还需要继续收敛到 `GameEnums` 与 `GameConstants`。
